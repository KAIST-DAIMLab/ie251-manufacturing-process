# TurtleBot3 Path-Finding System — Specification

**Target reader:** Claude Code (autonomous implementation agent)
**Project type:** ROS Noetic, Python (rospy), Gazebo simulation
**Hardware:** None for v1 (simulation only); design must support real TurtleBot3 Waffle later
**Robots:** Exactly 2, namespaces `tb3_0` and `tb3_1`

---

## 1. Project Overview

A centralized path-finding system for two TurtleBot3 Waffle robots operating on a 6m × 3m table modeled as a connected graph of nodes. A user requests a robot move to a target node by ID; a central server plans the shortest path through the graph and dispatches it to the robot's executor, which drives between waypoints using `/cmd_vel` while reporting pose via `/odom`. A collision monitor predicts pairwise collisions over a short horizon and stops involved robots when a collision is imminent.

### In scope (v1)
- Static graph loaded from YAML at server startup
- A* path planning over the graph
- Per-robot path execution with a simple proportional controller (no `move_base`, no costmaps)
- Pairwise collision prediction with linear extrapolation
- Gazebo simulation with two TurtleBot3 Waffles spawned at known offsets
- CLI user client (`rosrun` invocable) for sending goals

### Explicitly out of scope (v1)
- AMCL or any localization stack — pose comes directly from `/odom`
- `move_base` or any costmap-based navigation
- Dynamic graph editing, dynamic obstacle avoidance, replanning on conflict
- More than 2 robots (collision check is pairwise but hardcoded for 2 namespaces)
- Real hardware drivers (the design supports a swap, but no implementation in v1)
- Unit tests (acceptance is via launch + observation; see §9)

## 2. System Architecture

### Runtime topology (what processes run, and what they talk about)

```
┌─────────────────┐    MoveToNode action   ┌────────────────────────────────┐
│  client    │ ─────────────────────► │           path_server          │
│  (one-shot CLI) │                        │  ┌──────────────────────────┐  │
└─────────────────┘                        │  │ Graph + PathPlanner      │  │
                                           │  │ CollisionMonitor (10 Hz) │  │
                                           │  └──────────────────────────┘  │
                                           └──┬─────────────────┬───────────┘
                              FollowPath action │       FollowPath action │
                                                ▼                         ▼
                                ┌──────────────────────┐    ┌──────────────────────┐
                                │ tb3_0_executor (node)│    │ tb3_1_executor (node)│
                                │  TurtleBotExecuter   │    │  TurtleBotExecuter   │
                                └──┬─────────────┬─────┘    └──┬─────────────┬─────┘
                          /tb3_0/odom   /tb3_0/cmd_vel  /tb3_1/odom   /tb3_1/cmd_vel
                                ▼             ▲                ▼             ▲
                          ┌─────────────────────────────────────────────────────┐
                          │                       Gazebo                        │
                          │           (turtlebot3_gazebo, custom world)         │
                          └─────────────────────────────────────────────────────┘

         Collision monitor → executors:
         /tb3_0/emergency_stop  (std_msgs/Empty)   ← published by CollisionMonitor
         /tb3_1/emergency_stop  (std_msgs/Empty)   ← published by CollisionMonitor

         Robot state reporting:
         /tb3_0/robot_state     (pathfinder/RobotState)  ← published by executor
         /tb3_1/robot_state     (pathfinder/RobotState)  ← published by executor
```

### Number of ROS nodes
- **1** `path_server` node — owns Graph, PathPlanner, CollisionMonitor
- **2** `*_executor` nodes — one per robot (`tb3_0_executor`, `tb3_1_executor`)
- **1** `client` (transient — exits after the action result)
- **+ Gazebo + `turtlebot3_gazebo` nodes from upstream**

### Coordinate frame contract
- All positions are in the **world frame**, in **meters**.
- The world's origin is the bottom-left corner of the 6×3 table.
- Each robot is spawned in Gazebo at a known offset; the executor treats `/<ns>/odom` as already being in the world frame.
- **Do not** introduce AMCL, `tf`, or coordinate transforms. Spawn poses are configured in the launch file so that `/odom` ≈ world.

## 4. Message & Action Schemas

### `action/MoveToNode.action`
```
# Goal: tell the server which robot should go to which node
string  robot_id            # "tb3_0" or "tb3_1"
int32   target_node_id
---
# Result: did the robot reach the goal?
bool    success
string  message             # human-readable reason on failure
---
# Feedback: progress while underway
int32   current_node_id     # last waypoint reached (-1 if none yet)
int32   nodes_remaining
```

### `action/FollowPath.action`
```
# Goal: an ordered list of node IDs the robot must visit
int32[] node_ids
---
bool    success
string  message
---
int32   current_index       # which waypoint in node_ids the robot is currently driving to
geometry_msgs/Pose2D current_pose
```

### `msg/RobotState.msg`
```
string                  robot_id
geometry_msgs/Pose2D    pose
geometry_msgs/Twist     velocity
uint8                   status         # see RobotStatus enum below
time                    stamp
```

`RobotStatus` is a Python enum (§5.4); over the wire it serializes as a `uint8`:
`IDLE=0, MOVING=1, STOPPED=2, REACHED=3, ERROR=4`.

## 5. Class Specifications

The class structure mirrors the UML diagram exactly. Every class below is a Python class. Type hints in this section are **mandatory** in the implementation — they are part of the contract.

### 5.1 Package `world`

#### `Node` — `world/node.py`
```python
@dataclass(frozen=True)
class Node:
    id: int
    x: float                # world-frame meters
    y: float                # world-frame meters

    def distance_to(self, other: "Node") -> float: ...
```
Frozen dataclass — nodes are values, not entities. `distance_to` is Euclidean.

#### `Edge` — `world/edge.py`
```python
@dataclass(frozen=True)
class Edge:
    from_node: Node         # field name is `from_node` (Python keyword reasons)
    to_node: Node
    cost: float             # set to from_node.distance_to(to_node) at construction
```

#### `Graph` — `world/graph.py`
```python
class Graph:
    def __init__(self, nodes: list[Node], edges: list[Edge]) -> None: ...

    def get_node(self, node_id: int) -> Node: ...
    def get_neighbors(self, node: Node) -> list[Node]: ...
    def edge_cost(self, a: Node, b: Node) -> float: ...
    def has_edge(self, a: Node, b: Node) -> bool: ...

    @classmethod
    def load_from_yaml(cls, path: str) -> "Graph": ...
```
Internally: `nodes` stored as `dict[int, Node]`, `edges` as adjacency list `dict[int, list[Edge]]`. Edges are **undirected** — `load_from_yaml` adds each edge to both endpoints' adjacency lists. `edge_cost` raises `KeyError` if the pair is not connected; `has_edge` returns bool.

### 5.2 Package `planning`

#### `Path` — `planning/path.py`
```python
class Path:
    def __init__(self, waypoints: list[Node]) -> None: ...

    def next(self) -> Node: ...           # returns and advances cursor; raises StopIteration if complete
    def peek(self) -> Node: ...           # returns next without advancing
    def is_complete(self) -> bool: ...
    def remaining(self) -> list[Node]: ...
    def length(self) -> int: ...          # total waypoint count, not remaining
    def current_index(self) -> int: ...   # 0-based index of next waypoint to be returned
```
The cursor starts at 0. After `next()` returns the i-th waypoint, the cursor is at i+1.

#### `PathPlanner` — `planning/path_planner.py`
```python
class PathPlanner:
    def __init__(self, graph: Graph) -> None: ...
    def plan(self, start: Node, goal: Node) -> Path: ...
```
**Algorithm:** A* with Euclidean heuristic. Edge cost is `Graph.edge_cost`. If no path exists, raise `ValueError("no path from {start.id} to {goal.id}")`.

#### `PathServer` — `planning/path_server.py`
```python
class PathServer:
    def __init__(
        self,
        graph: Graph,
        planner: PathPlanner,
        monitor: CollisionMonitor,
        robot_namespaces: list[str],   # ["tb3_0", "tb3_1"]
    ) -> None: ...

    def start(self) -> None: ...
        # Starts the MoveToNode action server on /path_server/move_to_node
        # Creates one FollowPath action client per namespace in robot_namespaces

    def _on_move_to_node(self, goal: MoveToNodeGoal) -> None: ...
        # 1. Look up robot's current pose (from latest /<ns>/robot_state)
        # 2. Find nearest graph node to that pose -> start_node
        # 3. planner.plan(start_node, graph.get_node(goal.target_node_id)) -> Path
        # 4. Send FollowPath goal to /<ns>/follow_path with the node IDs
        # 5. Forward feedback/result back through the MoveToNode action
```
The server is responsible only for orchestration. It does **not** drive robots directly. It reads each robot's state from `/<ns>/robot_state` (subscribed at construction) to figure out the start node.

### 5.3 Package `safety`

#### `LinearPredictor` — `safety/linear_predictor.py`
```python
class LinearPredictor:
    def __init__(self, safety_radius: float, time_step: float) -> None: ...

    def will_collide(
        self,
        s1: RobotState,
        s2: RobotState,
        horizon: float,
    ) -> bool: ...
```
**Contract:** at each `t in [0, time_step, 2*time_step, ..., horizon]`, extrapolate each robot's pose forward using its current velocity (linear in body x, angular in z). Return True if at any sampled t the Euclidean distance between the two extrapolated positions is less than `safety_radius`.

Default values (set in `params.yaml`): `safety_radius=0.35`, `time_step=0.1`.

#### `CollisionMonitor` — `safety/collision_monitor.py`
```python
class CollisionMonitor:
    def __init__(
        self,
        predictor: LinearPredictor,
        robot_namespaces: list[str],
        horizon: float,
        check_rate_hz: float,
    ) -> None: ...

    def start(self) -> None: ...
        # Subscribes to /<ns>/robot_state for each ns
        # Creates publishers for /<ns>/emergency_stop (std_msgs/Empty)
        # Starts a rospy.Timer at check_rate_hz that calls _tick()

    def update_state(self, ns: str, state: RobotState) -> None: ...
        # Subscriber callback. Stores latest state.

    def _tick(self, event) -> None: ...
        # Called by Timer. For each pair of robots (only one pair for v1):
        # if predictor.will_collide(s1, s2, horizon): publish Empty to BOTH /<ns>/emergency_stop.
```
Default `horizon=2.0`, `check_rate_hz=10.0` (from `params.yaml`).

The monitor publishes a stop signal — it does **not** import or call into `TurtleBotExecuter`. This is deliberate (decoupling).

### 5.4 Package `robot`

#### `RobotStatus` — `robot/robot_status.py`
```python
from enum import IntEnum
class RobotStatus(IntEnum):

    MOVING  = 1
    STOPPED = 2
    REACHED = 3
    ERROR   = 4
```

#### `RobotState` — `robot/robot_state.py`

@dataclass
class RobotState:

    status: RobotStatus

#### `TurtleBotExecuter` — `robot/turtlebot_executer.py`
This is the most complex class. It owns the per-robot control loop.

```python
class TurtleBotExecuter:
    def __init__(
        self,
        robot_id: str,                  # "tb3_0" or "tb3_1"
        graph: Graph,                   # needed to look up node coordinates by ID
        controller_params: dict,        # gains, tolerances; loaded from params.yaml
    ) -> None: ...

    def start(self) -> None: ...
        # Subscribes:  /<ns>/odom              (nav_msgs/Odometry)
        # Subscribes:  /<ns>/emergency_stop    (std_msgs/Empty)
        # Publishes:   /<ns>/cmd_vel           (geometry_msgs/Twist)
        # Publishes:   /<ns>/robot_state       (pathfinder/RobotState) at 10 Hz
        # Action srv:  /<ns>/follow_path       (FollowPath)
        # Starts the control loop timer at 20 Hz.

    # --- Action server callback ---
    def _on_follow_path(self, goal: FollowPathGoal) -> None: ...
        # Set self._active_path from goal.node_ids
        # Set status = MOVING
        # Block (using rospy rate) until path complete OR preempted OR stop_requested
        # Publish FollowPath result with success bool

    # --- Topic callbacks ---
    def _on_odom(self, msg) -> None: ...                # update self._state.pose, .velocity
    def _on_emergency_stop(self, msg) -> None: ...      # set self._stop_requested=True; status=STOPPED

    # --- Periodic ---
    def _control_tick(self, event) -> None: ...
        # If no active path or stop_requested: publish zero Twist; return.
        # Else: target = active_path.peek() -> world coords from graph
        #       compute Twist via simple proportional controller (see below)
        #       if distance to target < arrival_tol: active_path.next();
        #           if active_path.is_complete(): status=REACHED; clear path
        #       publish Twist on /<ns>/cmd_vel

    def _publish_state_tick(self, event) -> None: ...
        # Publish self._state to /<ns>/robot_state
```

**Controller:** simple two-stage proportional (no library needed). Given current pose `(x, y, θ)` and target `(tx, ty)`:
1. Compute heading error: `θ_err = atan2(ty - y, tx - x) - θ`, wrap to `[-π, π]`.
2. If `|θ_err| > heading_tol` (e.g. 0.2 rad): rotate in place — `linear.x = 0`, `angular.z = clamp(k_ang * θ_err, ±max_ang_vel)`.
3. Else: drive forward — `linear.x = clamp(k_lin * distance, ±max_lin_vel)`, `angular.z = clamp(k_ang * θ_err, ±max_ang_vel)`.
4. If `distance < arrival_tol`: arrived.

Default `controller_params` (from `params.yaml`):
```yaml
k_lin: 0.5
k_ang: 1.5
max_lin_vel: 0.22         # TB3 Waffle max
max_ang_vel: 1.5
arrival_tol: 0.10
heading_tol: 0.2
```

## 6. ROS Node Entry Points

Each script in `scripts/` is short. **No business logic** — only ROS init, param loading, and class instantiation.

### `scripts/path_server_node`
```
1. rospy.init_node("path_server")
2. Load graph YAML path from rosparam ~graph_file
3. Load params.yaml values from rosparam (~horizon, ~check_rate_hz, etc.)
4. graph = Graph.load_from_yaml(graph_file)
5. planner = PathPlanner(graph)
6. predictor = LinearPredictor(safety_radius, time_step)
7. monitor = CollisionMonitor(predictor, ["tb3_0", "tb3_1"], horizon, check_rate_hz)
8. server = PathServer(graph, planner, monitor, ["tb3_0", "tb3_1"])
9. monitor.start(); server.start()
10. rospy.spin()
```

### `scripts/robot_executor_node`
```
1. rospy.init_node("executor")  # actual node name set by launch file (tb3_0_executor, etc.)
2. robot_id = rospy.get_param("~robot_id")  # "tb3_0" or "tb3_1"
3. graph = Graph.load_from_yaml(rospy.get_param("~graph_file"))
4. controller_params = rospy.get_param("~controller")  # dict from params.yaml
5. executer = TurtleBotExecuter(robot_id, graph, controller_params)
6. executer.start()
7. rospy.spin()
```

### `scripts/client`
```
1. parse argv: robot_id, target_node_id
2. rospy.init_node("client", anonymous=True)
3. client = Client()
4. ok = client.send_goal(robot_id, int(target_node_id))
5. sys.exit(0 if ok else 1)
```

## 7. Configuration

### `config/graph.yaml` — the agent must commit this exact file

Six nodes in a 3×2 grid on the 6m×3m table. Bottom row (y=0.75): N0, N2, N4 from left to right. Top row (y=2.25): N1, N3, N5 from left to right. Seven edges: top row, bottom row, and three verticals.

```
   N1 ─── N3 ─────── N5         (top row,    y = 2.25)
   │       │          │
   │       │          │
   N0 ─── N2 ─────── N4         (bottom row, y = 0.75)
```

```yaml
nodes:
  - {id: 0, x: 1.0, y: 0.75}     # bottom-left
  - {id: 1, x: 1.0, y: 2.25}     # top-left
  - {id: 2, x: 3.0, y: 0.75}     # bottom-middle
  - {id: 3, x: 3.0, y: 2.25}     # top-middle
  - {id: 4, x: 5.0, y: 0.75}     # bottom-right
  - {id: 5, x: 5.0, y: 2.25}     # top-right

edges:
  # Bottom row
  - {from: 0, to: 2}
  - {from: 2, to: 4}
  # Top row
  - {from: 1, to: 3}
  - {from: 3, to: 5}
  # Verticals
  - {from: 0, to: 1}
  - {from: 2, to: 3}
  - {from: 4, to: 5}
```

**Note on graph symmetry:** this graph has multiple shortest paths between many node pairs (e.g. N0→N5 has two equal-length 3-edge routes via either N1 or N2). `PathPlanner` must use a deterministic tiebreak: **prefer the neighbor with the lower node ID when A* costs are tied**. This makes test outcomes reproducible.

## 8. Gazebo Setup

### `worlds/pathfinding_table.world`
A flat ground plane sized 6m × 3m with no obstacles. The agent can copy `turtlebot3_gazebo`'s `empty.world` and resize the floor, or generate from scratch — either is acceptable. Lighting and physics defaults are fine.

### `launch/gazebo_world.launch`

Launches everything needed to run the system end-to-end:

1. Sets `TURTLEBOT3_MODEL=waffle` (env or arg).
2. Starts `gazebo_ros empty_world.launch` with `world_name:=$(find pathfinder)/worlds/pathfinding_table.world`.
3. Spawns two TurtleBot3 Waffles using `spawn_model` (URDF from `turtlebot3_description`):
   - `tb3_0` at `(x=1.0, y=0.75, yaw=0)` — coincides with graph node 0
   - `tb3_1` at `(x=5.0, y=2.25, yaw=π)` — coincides with graph node 5
   - Each spawned under its own namespace (`<group ns="tb3_0">...</group>`)
   - Each robot's URDF must have `tf_prefix` set so frames don't collide
4. Loads `config/params.yaml` onto the parameter server under `/path_server` and `/<ns>/executor`.
5. Starts:
   - `path_server_node` (no namespace) — name `path_server`
   - `robot_executor_node` in namespace `tb3_0` with name `executor` and param `~robot_id:=tb3_0`
   - `robot_executor_node` in namespace `tb3_1` with name `executor` and param `~robot_id:=tb3_1`

The agent **must reference `turtlebot3_gazebo`'s `multi_turtlebot3.launch`** as the canonical pattern for spawning multiple TB3s with namespaces — do not invent a new approach.

### `launch/system.launch`
Same as `gazebo_world.launch` but **without** Gazebo and without spawning robots. Useful when running against a different sim or for debugging the node graph in isolation.

## 9. Acceptance Criteria

The implementation is complete when **all** of the following pass. Each test is a runnable command sequence; the expected outcome is observable via `rostopic echo`, RViz, or visual inspection of Gazebo.

### AC-1: Build succeeds
```bash
cd ~/repositories/kaist/ie251-manufacturing-process && catkin_make
source devel/setup.bash
```
**Expected:** zero errors. Action and message generation produce `pathfinder/msg/RobotState.py`, `pathfinder/msg/MoveToNodeAction.py`, etc.

### AC-2: Gazebo launches with two robots at correct poses
```bash
roslaunch pathfinder gazebo_world.launch
```
**Expected:** Gazebo opens. Two TurtleBot3 Waffles visible — one near the bottom-left, one near the top-right of the 6×3 floor. `rostopic list` shows both `/tb3_0/odom` and `/tb3_1/odom`.

### AC-3: Robot states are published
With AC-2 running, in another terminal:
```bash
rostopic echo /tb3_0/robot_state
```
**Expected:** ~10 Hz stream of `RobotState` messages. `pose.x ≈ 1.0`, `pose.y ≈ 0.75`, `status: 0` (IDLE).

### AC-4: Single-robot path execution
With AC-2 running:
```bash
rosrun pathfinder client tb3_0 5
```
**Expected:**
- Client prints feedback as `tb3_0` advances through waypoints. Expected sequence given the lower-ID tiebreak: **N0 → N1 → N3 → N5**.
- In Gazebo, `tb3_0` drives along graph edges from N0 to N5 via N1 and N3 (top route).
- Final result: `success: true`.
- `tb3_0`'s final pose ≈ `(5.0, 2.25)` within 10 cm.

### AC-5: Two-robot independent execution (no collision)
With AC-2 running, in two separate terminals:
```bash
rosrun pathfinder client tb3_0 4     # bottom row: N0 → N2 → N4
rosrun pathfinder client tb3_1 1     # top row:    N5 → N3 → N1
```
**Expected:** both robots drive along their rows in parallel. They are 1.5m apart vertically (top row at y=2.25 vs bottom row at y=0.75) — well outside the 0.35m safety radius. No emergency stop fires. Both succeed.

### AC-6: Collision avoidance triggers stop

## 11. Glossary & Conventions

- **Robot namespace (`<ns>`)** — always `tb3_0` or `tb3_1`. Hardcoded throughout.
- **World frame** — the single frame all positions are reported in. Origin = bottom-left of table.
- **Node ID** — `int32`, unique within a graph. The graph YAML defines them.
- **Waypoint** — a `Node` the robot is currently driving toward. The active `Path` tracks the cursor.
- **Action** — ROS actionlib (not topic, not service). Use `actionlib.SimpleActionServer` and `SimpleActionClient`.
- **Pose source** — `nav_msgs/Odometry` from `/<ns>/odom`. No AMCL, no `tf` lookups.
- **Stop signal** — `std_msgs/Empty` on `/<ns>/emergency_stop`. One-shot; the executor stays stopped until a new `FollowPath` goal arrives.

### Naming conventions
- Python: `snake_case` for files, functions, variables; `CamelCase` for classes.
- ROS topics: lowercase with underscores, namespaced (`/tb3_0/cmd_vel`).
- ROS params: snake_case, namespaced under the node.
- File names match class names (`turtlebot_executer.py` → `class TurtleBotExecuter`).

### Things the implementation must NOT do
- Catch and silently swallow exceptions in callbacks — let them propagate so failures are visible.
- Use global state. Everything is owned by class instances.
- Hardcode node count beyond 2 in v1, but leave the door open: anywhere "2" appears, prefer iterating over `robot_namespaces`.
- Import ROS message types at module top level in non-script files unless needed — keeps the OOP classes testable in principle.
- Skip type hints. Every public method must be fully typed.
